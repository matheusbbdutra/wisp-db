# ADR 0006 — UI localization via `i18next`/`react-i18next`

**Status:** Accepted
**Date:** 2026-09-16

## Context
The app's UI (buttons, labels, error messages) has been Brazilian Portuguese throughout since the project's inception, written by and for the maintainer's own daily use. As the project goes open source, an English-first UI (with a language switch back to Portuguese for the maintainer) becomes a real requirement, not a speculative one — this was already flagged as a known gap in `docs/ROADMAP.md`.

## Decision
- Use **`i18next` + `react-i18next`** (checked against the live npm registry on 2026-09-16: `i18next@26.4.2`, `react-i18next@17.0.14`, both MIT, both actively maintained) — the de facto standard pairing for React i18n, rather than hand-rolling a translation mechanism.
- **Structure**: `frontend/src/i18n/index.ts` (init) + `frontend/src/i18n/locales/en.json` + `frontend/src/i18n/locales/pt-BR.json`. Flat, component-namespaced keys (e.g. `sidebar.search`, `resultGrid.filterPlaceholder`) — no deep nesting, easy to grep.
- **Default language**: detected from the OS/browser locale (`navigator.language`) on first run — `pt-BR`/`pt` maps to the Portuguese locale, anything else falls back to English. A saved preference in `localStorage` (`wisp:language`) always wins once the user picks one explicitly via a language selector in the tab bar (next to "Verificar atualização"/"Check for updates").
- **Scope**: every user-facing string in the React components, plus the fixed error-message prefixes written in Go (`app.go`, `internal/db/*.go` — e.g. `"erro ao salvar célula: %w"`) move to English. The Go side does **not** get real i18n (no locale plumbed through IPC) — those strings are just switched to English text, since the underlying driver errors (pgx/SQLite) are already in English in practice and there's no case for the backend supporting two languages independently of the frontend's chosen language.
- **Out of scope**: internal working notes (`STATE.md`, `CLAUDE.md`) stay Portuguese — never repo-facing. **Update 2026-09-16**: Go source comments (`.go` files) move to English too, per an explicit project-wide language policy (see `CLAUDE.md`, "Idioma") — new comments already in English going forward; existing Portuguese comments migrate in a dedicated future pass, not required immediately. TSX/TS comments in the frontend were not part of that decision and remain Portuguese until decided otherwise.

## Alternatives considered
- **Hand-rolled translation (a plain lookup object, no library)**: rejected — `i18next`/`react-i18next` already solve pluralization, interpolation, and namespace organization correctly; reinventing this has the same "no benefit, same maintenance cost" problem the project already avoided for SQL formatting (ADR 0005) and the data grid (ADR 0001).
- **`react-intl` (FormatJS)**: also solid and MIT-licensed, but `i18next` was chosen for its simpler flat-JSON key model, which fits the project's preference for explicit, greppable code over convention-heavy abstractions.
- **Full locale-aware Go backend**: rejected — no real need identified; the backend's error strings are implementation details surfaced verbatim in the UI, not a distinct localization surface.

## Consequences
- New npm dependency (`i18next` + `react-i18next`) — checked: trustworthy, active, MIT.
- Every component with user-facing text needs a pass to replace literal strings with `t('key')` calls — done incrementally, reviewed component by component (build/typecheck after each), not as one giant unreviewed diff.
- Adding a third language later means adding one more JSON file plus one more `<option>` in the language selector — no architecture change required.
